## Goal

Clear the nine Angular compiler warnings reported by the dev-server watch build:

- 3 × `TS-998113` — standalone `imports` arrays referencing components/directives that are not used
  in the component templates.
- 6 × `NG8107` — optional chaining (`?.`) on expressions the type system already proved
  non-nullable, so the `?.` was flagged as removable.

---

## Completed

- **Removed 3 unused standalone imports** (no behaviour change — the components were never
  referenced in the templates):
  - `SignaturePadLibComponent` from `ScmVerificationProcessComponent` (the signature pad is used
    by `scm-verification-modal.component.ts` and `scm-step-collection.component.ts`, which keep
    their own imports — only the parent was stale).
  - `RouterLink` from `CompanyShellComponent` and `ComplianceShellComponent`. Both shells render
    navigation through `app-tab-bar`, which imports `RouterLink` itself; the shells only need
    `RouterOutlet`.
- **Cleared 6 `NG8107` warnings** by fixing the underlying types rather than by deleting the
  `?.` that was genuinely guarding against a runtime `null`:
  - `gps-hierarchy.page.ts` — `tasks()[t.id]?.length` / `updates()[t.id]?.length` are index
    lookups into `Record<number, GpsTask[]>` / `Record<number, GpsUpdate[]>`, which TypeScript
    treats as always-present. Replaced with the existing `taskCount(targetId)` helper and a new
    `updateCount(targetId)` helper (both already null-safe via `|| []`), so the template reads a
    plain number and the guard now lives in one place instead of being duplicated in the markup.
  - `results.page.ts` — `c.by_status?.['verified']` on the `AchievementCounts` interface. The
    backend (`Achievement::countsByCompany`) always returns `by_status`, but the service declared
    it as a required `Record<string, number>`, so the optional chain looked redundant to the
    compiler while the template still defensively guarded it. `by_status` is now declared
    optional (`by_status?: Record<string, number>`), matching how the value is actually consumed
    (`c?.by_status?.['verified'] || 0` in `dashboard-cards.component.ts`) and keeping the runtime
    guard intact.
  - `sessions-page.component.ts` — `nextSession()?.subject` where `nextSession` is
    `computed(() => this.upcomingSessions()[0] ?? null)`. Array index access on `SessionSummary[]`
    is typed as `SessionSummary` (not `SessionSummary | undefined`), so the `?? null` was erased
    from the inferred type and the compiler concluded the result was never null. The computed is
    now explicitly typed `computed<SessionSummary | null>(...)`, which restores the true type and
    keeps the template's `?.` and the `@if (nextSession(); as next)` block valid.
- **Verified** with `ng build --configuration development` — the build now completes with **zero
  warnings and zero errors** (previously 9 warnings). Full build log was captured and grepped for
  `WARNING|ERROR|TS####|NG####` to confirm nothing was hidden by console truncation.

## Decisions

- **Fixed the type, not the warning.** For the `NG8107` cases the `?.` operators were guarding
  against genuinely-possible `null`/`undefined` values that the type system had wrongly narrowed
  away. Deleting the `?.` (as the diagnostic text suggests) would have introduced runtime
  `TypeError`s on empty result sets. Each warning was resolved by restoring the truth in the
  type, so the existing runtime guards stay in place.
- **Reused the existing `taskCount` helper** in `gps-hierarchy.page.ts` rather than introducing a
  new inline expression, so the null-safe `|| []` fallback is defined once and the template stays
  declarative.
- **Did not touch the legacy financial screens** or any other surface — the changes are confined
  to the six files that produced the reported diagnostics.
