## Decisions

- **One combined runner, not one more suite.** `GoogleCalendar.ps1` orchestrates the existing suites, refuses to run without the fake, and is the single sprint-level proof. It never contacts Google.
- **The ownership model is documented before deployment.** The central-account model is written into the API reference, the console runbook and the deployment runbook so nobody introduces multi-user publishing ad hoc.
- **Multi-user publishing is explicitly future work.** It is a **tenant-owned connection** with its own migration and authorization model — recorded in "Reserved future modules" and the deployment runbook, not built now.
- **A single-row verifier.** `verify-google-compact.sql` follows the proven compact pattern (one `SELECT`, no `UNION ALL`) so it renders reliably on the production phpMyAdmin; the token invariant checks that a cipher never exists without its nonce/tag.
- **The deployment runbook treats the eight edited pre-existing files as a distinct layer.** They are additive, post-commit, no-op-defaulted hooks; rollback is a plain file restore.
- **The exposed credential was removed from disk but the rotation is an operator action.** Incubator OS cannot rotate a Google password; the doc states exactly what the operator must do (rotate + 2FA) and never stores the value.

## Deploy hold-point — verifier defect found and fixed (2026-09-24, continued)

The operator ran the pre-deploy preflight against production `rbttaces_api`.

**Prior-sprint grid (accepted, no blocker):** `db=rbttaces_api`, `mysql_version=8.0.46-cll-lve`,
`t_007a=3`, `c_007a=1`, `i_007b=1`, `t_008=2`, `chk_008=1`, `t_009=7`, `fk_009=1`,
`unresolved_rows=100`, `export_account_companies=0`. Every prior-sprint object is
`PRESENT` — no partial, no invalid, no drift.

**Google grid:** the first single-file verifier raised
`#1146 - Table 'rbttaces_api.google_calendar_connections' doesn't exist`.

**Cause (a real defect in the verifier):** MySQL resolves every table named in a query
at parse time. The verifier's two integrity lines read
`FROM google_calendar_connections` directly, so on a pre-deploy database the whole
statement failed at parse time — the `information_schema`-only columns were never
reached, and the header's "never errors on a pre-deploy database" claim was false.

**Fix:** split the verifier into two files following the repo's established pattern:

- `docs/deployment/verify-google-compact.sql` — **structure**, `information_schema`
  only, never names a Google table in a `FROM`; safe **before and after**.
- `docs/deployment/verify-google-integrity-compact.sql` — **data invariants** (token/
  cipher integrity, orphan projection, cross-tenant, one-connection-per-user); reads
  the Google tables and therefore runs **only after** the migrations.

**Proof:** the structure file returns **all zeros** against a real pre-010 schema
(`incubator_os_prod`, which lacks the Google tables) with **no `#1146`**, and all ones
against the migrated local DB; the integrity file returns every `inv_* = 0` locally.
Both files contain exactly one statement and one semicolon, and are pure ASCII.

The runbook (`docs/sprint-010-google-calendar-deployment.md` §3, Step 5, Step 8) and
the sprint were updated to the two-file split, with the cause documented so the same
mistake is not repeated.

**Verdict: the hold-point does NOT yet clear** — the corrected structure verifier must
be run against production and return a clean all-zero Google row before migrations
#22–#25 are applied. Nothing has been applied.

## Backend upload — misconfiguration found and fixed (2026-09-24, continued)

The operator uploaded the backend via FileZilla. Reviewing the FTP log exposed a
**serious deployment misconfiguration**: the **local dev** `config/google.local.php`
(427 bytes, `use_fake => true`, placeholder `local-fake-client`/`local-fake-secret`,
shared test AES key `iH3yi0z…`) was uploaded to production `/api/config/`, together
with `google.local.example.php`. Consequences: (1) `use_fake => true` would make
Connect point at a fake OAuth client and never reach real Google; (2) the shared test
key is in every developer's working tree; (3) no real token had been minted yet, so
it is fully recoverable.

Also noted from the log: `/api/config/error_log` was deleted by FileZilla (logs must
never be touched), and the whole `capabilities/` + `api/` folders were uploaded
including `capabilities/company` and `capabilities/financial-indicators` — those are
**byte-identical to production** (no diff since `2732e3b`), so that part is a
harmless no-op.

**Fix shipped (commit `942e597`):** `config/google.php` now fails closed when the
offline fake is configured on a **non-loopback** host.

- `google_use_fake()` honours the fake only when requested AND `APP_URL` is loopback
  (`localhost` / `127.0.0.1` / `::1`).
- `google_config_error()` returns a safe error when `use_fake` is requested on a
  non-loopback host, so `google_configured()` is false and every Google endpoint
  returns `503 GOOGLE_NOT_CONFIGURED` — it can no longer silently run placeholder
  credentials. An unresolvable `APP_URL` fails closed too.
- **Proof:** on `https://app.rbttacesd.co.za` the host check is false and
  `google_use_fake()` stays false **even with `GOOGLE_FAKE=1`**; on
  `http://localhost:8080` the fake is allowed. Phase 1 gained two assertions
  (**64/64**); the combined runner is **490/490**.

**Operator remediation added to the runbook:** Step 3b — delete the uploaded
`google.local.php` and `google.local.example.php`, create a fresh
`config/google.local.php` **by hand** with the real client id/secret and a **newly
generated** AES key (never reuse the shared test key), re-upload the committed
`config/google.php`, never touch `error_log`, then re-check. Step 3 and Step 4 were
rewritten to forbid dragging the whole `config/` folder.

**Status:** the backend files are deployed, but the **credential step must be
redone** before the Google connect/token step. No real token exists yet; no token
was ever encrypted with the shared key.
